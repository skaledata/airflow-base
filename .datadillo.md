# Datadillo review guidance — skaledata/airflow-base

The custom Airflow base Docker image used by SkaleData customer clusters.
Layers on top of the upstream `apache/airflow` image with SkaleData-specific
providers, config, and defaults. Deployed to customer clusters via the
Helm-native app lifecycle (Phase 27); pulled by the SkaleData control plane's
Custom Airflow Images UI (Phase 30). See `README.md` for the release model
and `CLAUDE.md` for repo orientation.

## Highest-signal review dimensions (in order)

1. **Airflow major/minor compatibility.** Supported Airflow versions are
   enumerated in `versions.json` — every entry there gets a mutable +
   immutable GHCR tag, and the entry flagged `latest: true` gets the
   floating `:latest` tag. Reject any change that would break compatibility
   with a version listed there unless the entry is being removed in the
   same PR. The SkaleData platform pins a specific Airflow version per
   platform release — check `apps/api/api/compatibility.json` in the
   `skaledata/skaledata` repo before assuming a version is safe to drop.
2. **`versions.json` contract.** Every entry needs `airflow` + `python`.
   At most one entry may have `latest: true` (enforced by the
   `setup-matrix` job — flag any PR whose CI would fail this). Adding a
   new Airflow version should be a one-line edit; anything that
   duplicates the matrix into `ci.yml` / `release.yml` is a regression.
3. **Plugin cross-version compatibility.** `package/` ships one plugin
   built into *every* image in `versions.json`. Any diff that imports
   from `airflow.providers.*` needs to work against every listed Airflow
   version. CI runs the plugin's `pytest` suite inside each built image —
   removing that step, or making a test skip on a specific Airflow
   version without a very concrete justification, is a regression.
4. **Dockerfile reproducibility.** The base image inherits from
   `apache/airflow:<version>-python<version>`, pinned via build-args
   supplied from `versions.json`. Flag: (a) reintroducing a default for
   `ARG AIRFLOW_VERSION` / `ARG PYTHON_VERSION` (dropped on purpose so a
   naked `docker build` fails loudly), (b) any FROM that pulls `:latest`
   or an unpinned tag, (c) `pip install` without a constraints file where
   the base image already provides one.
5. **Release model integrity.** Two tag prefixes, distinct concerns:
   - `image-v*` → rebuild every entry in `versions.json` to GHCR
   - `plugin-v*` → publish `airflow-provider-skaledata` to PyPI, must
     match `package/pyproject.toml`'s `version` exactly
   Reject any diff that reintroduces the old `v*` trigger, removes the
   tag/pyproject match check, or couples the two channels (e.g. making
   image builds depend on a PyPI publish).
6. **Provider version compatibility.** Airflow provider packages must
   be compatible with the pinned Airflow version. Flag any provider bump
   that crosses a major boundary without a corresponding Airflow version
   note.
7. **`webserver_config.py` auth changes.** This file wires the FAB auth
   backend. Any change here can lock users out of Airflow — verify it
   preserves the current auth backend and role mappings. The baked-in
   default (`AUTH_ROLE_PUBLIC = "Admin"`) is intentional: SkaleData
   proxies validate the `sdk_*` API key at the edge, so an inner login
   screen would just be noise. Reject changes to this default that don't
   also update the customer-facing README and confirm the proxy-side
   authz is still in place.
8. **DAG parsing cost.** The scheduler parses every DAG file on the
   configured interval. Heavy imports or side effects at module top-level
   in anything under provider hooks/operators/triggers will tank
   scheduler throughput — flag hard.

## Review economy (do this to avoid multi-round churn)

Surface **all** issues in the first pass, grouped by severity — don't
dribble one blocker per round. When you flag a pattern (e.g. "reintroduces
the old `v*` trigger"), check whether the same class of bug appears
elsewhere in the diff and list every instance. If a snippet you suggest
depends on a repo detail, verify it: e.g. the plugin's Airbyte hook
subclasses `airflow.providers.airbyte.hooks.airbyte.AirbyteHook` — a
suggested override that names a method the upstream class doesn't expose
is itself a bug.

## Repo-specific gotchas (flag these hard)

- **Do not add tenant-specific config.** This image is shared across all
  customer clusters. Anything customer-specific belongs in the SkaleData
  cluster config, not the image.
- **`AIRFLOW__CORE__EXECUTOR`** — set by the Helm chart, not the image.
  Reject any `ENV` that hard-codes an executor.
- **`airflow db migrate` at image build time is wrong.** The migration
  runs at chart install/upgrade against the cluster's Postgres — the
  image must not attempt DB access during build.
- **Python version drift.** Airflow 3.x supports Python 3.10–3.12; pick
  ONE per Airflow version in `versions.json` and stick with it. Flag any
  diff that mixes Python versions across build stages of a single image.
- **ONBUILD triggers are customer contract.** `packages.txt` (apt) and
  `requirements.txt` (pip) auto-pickup is the promised
  Astronomer-compatible convention. The pip step deliberately does NOT
  pass `--constraint` — reintroducing it blocks legitimate customer
  provider bumps. Flag any change that would break either file's
  auto-pickup, including the comment/blank-line filtering.
- **Plugin entry point registration.** `package/pyproject.toml` declares
  `[project.entry-points."airflow.plugins"]` for `AirbytePlugin`. If a
  new plugin class is added, verify it's registered here — otherwise
  Airflow won't pick it up when the plugin is installed from PyPI
  (works inside the image only by accident of pip-editable install).
- **Ruff formatting.** CI runs `ruff format --check` in `package/`.
  A diff that fails formatting is a hard block, not a nit — CI won't
  merge it.

## What to skip

- Version bumps in `requirements.txt` where tests still pass and it's
  a patch-level rev.
- README / CLAUDE.md / doc-only edits that don't change behavior.
- Lockfile diffs unless a suspicious dep was added.
- Ruff config nits — the linter gates these already.
- One-line typo fixes in comments or user-facing strings.

## Tone

Terse and actionable. Where a finding could break a customer cluster on
next chart upgrade — or break a customer's downstream `FROM` — say so
explicitly. If a finding is speculative, say so and offer a concrete
verification step.
