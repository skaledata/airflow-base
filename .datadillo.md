# Datadillo review guidance — skaledata/airflow-base

The custom Airflow base Docker image used by SkaleData customer clusters.
Layers on top of the upstream `apache/airflow` image with SkaleData-specific
providers, config, and defaults. Deployed to customer clusters via the
Helm-native app lifecycle (Phase 27); pulled by the SkaleData control plane's
Custom Airflow Images UI (Phase 30).

## Highest-signal review dimensions (in order)

1. **Airflow major/minor compatibility.** The current SkaleData platform
   version (2026.05) pins **Airflow 3.2.1 on chart 1.21.0**. Workers live
   under `workers.celery.*` paths (Airflow 3 shape). Reject any change that
   would break compatibility with the pinned platform version unless
   explicitly bumping it.
2. **Dockerfile reproducibility.** The base image should be pinned by
   digest (or at least by exact tag) — not `latest`. Multi-stage builds
   should minimize final layer size. `pip install` commands need pinned
   versions (or a `requirements.txt` with hashes for reproducibility).
3. **Provider version compatibility.** Airflow provider packages must be
   compatible with the pinned Airflow version. Flag any provider bump that
   crosses a major boundary without a corresponding Airflow version note.
4. **`webserver_config.py` auth changes.** This file wires the FAB auth
   backend. Any change here can lock users out of Airflow — verify it
   preserves the current auth backend (OAuth/OIDC) and role mappings.
5. **DAG parsing cost.** The scheduler parses every DAG file on the
   configured interval. Heavy imports or side effects at module top-level
   in anything under `dags/` or provider hooks will tank scheduler
   throughput — flag hard.

## Repo-specific gotchas (flag these hard)

- **Do not add tenant-specific config.** This image is shared across all
  customer clusters. Anything customer-specific belongs in the SkaleData
  cluster config, not the image.
- **`AIRFLOW__CORE__EXECUTOR`** — this is set by the Helm chart, not the
  image. Reject any `ENV` that hard-codes an executor.
- **`airflow db migrate` at image build time is wrong.** The migration
  runs at chart install/upgrade against the cluster's Postgres — the
  image should not attempt DB access during build.
- **Python version drift.** Airflow 3.x supports Python 3.10–3.12; pick
  ONE and stick with it. Flag any diff that mixes Python versions across
  build stages or forgets to update the base image tag.

## What to skip

- Version bumps in `requirements.txt` where the tests still pass and it's
  a patch-level rev.
- README / docs edits that don't affect behavior.
- Lockfile diffs unless a suspicious dep was added.

## Tone

Terse. Where a finding could break a customer cluster on next chart
upgrade, say so explicitly.
